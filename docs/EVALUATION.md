# Evaluation results

Measured on the local stack, 2026-09-02. Apple Silicon, CPU only, 202 synthetic
Azerbaijani entries, 24 golden cases + 4 out-of-scope.

Reproduce with `python -u evals/run_eval.py`.

---

## Retrieval quality

| Pipeline | hit@1 | hit@3 | hit@5 | MRR | misses |
|---|---:|---:|---:|---:|---:|
| Keyword only | 79.2% | 87.5% | 87.5% | 0.826 | 3 |
| Vector only | **100.0%** | 100.0% | 100.0% | **1.000** | 0 |
| Hybrid RRF (no rerank) | 91.7% | 100.0% | 100.0% | 0.951 | 0 |
| Hybrid + reranker | 91.7% | 100.0% | 100.0% | 0.958 | 0 |

**Read this table sceptically.** Vector-only scoring a perfect 100% at hit@1 does
not mean the reranker is useless — it means *this dataset is too easy to
discriminate between pipelines*, for two compounding reasons:

1. The content was generated by an LLM, so it is unusually consistent in
   vocabulary and phrasing — far more so than knowledge bases written by humans
   over several years.
2. The golden questions were written against that same content. Even when
   deliberately paraphrased, they share its conceptual framing.

This is exactly the self-consistency trap documented in `evals/golden_set.py`. The
comparison only becomes meaningful once real ministry content and an
expert-written golden set replace both halves.

What the table *does* establish: keyword-only search is measurably worse (87.5%
hit@3, 3 outright misses), which confirms Azerbaijani morphology defeats
unstemmed full-text search, and justifies the vector half of the hybrid.

## The reranker earns its place elsewhere

Even where it does not improve hit@1, the cross-encoder produces the **calibrated
confidence score the escalation gate depends on**. Cosine similarity does not
separate relevant from irrelevant nearly as cleanly:

| | in-scope | off-topic |
|---|---|---|
| Rerank score — min | 0.0047 | 0.0000 |
| Rerank score — p10 | 0.3194 | — |
| Rerank score — median | **0.9679** | — |
| Rerank score — max | 0.9987 | **0.0033** |

Three orders of magnitude between the in-scope median and the off-topic ceiling.
That separation is what makes the gate reliable.

## Out-of-scope rejection

| Threshold | Rejected |
|---|---|
| 0.45, with a double sigmoid (original) | 0 / 4 ❌ |
| 0.10, sigmoid bug fixed (current) | **4 / 4** ✅ |

### The bug

`sentence-transformers`' `CrossEncoder` already applies a sigmoid for single-label
rerankers (`activation_fn=Sigmoid()`). The original `_confidence()` applied a
second one.

Consequences: every score was squeezed into `sigmoid(0)=0.500` to
`sigmoid(1)=0.731`. Any threshold below 0.5 became unreachable, so **nothing was
ever escalated** — off-topic questions included. The signature was a confidence
distribution suspiciously bounded by exactly 0.500 and 0.731.

Worth noting how it surfaced: the retrieval numbers looked fine, because ranking
is unaffected by a monotonic transform. Only the out-of-scope test caught it. A
suite that measured retrieval alone would have shipped this.

## Latency

Per-stage, averaged over 24 queries, CPU:

| Stage | 20 candidates | 10 candidates | 5 candidates |
|---|---:|---:|---:|
| Vector search | 54 ms | 55 ms | 54 ms |
| Keyword search | 11 ms | 11 ms | 11 ms |
| **Reranking** | **1144 ms** | **637 ms** | **310 ms** |
| Total retrieval | 1209 ms | 703 ms | 375 ms |

Reranking is ~95% of retrieval cost, roughly 57ms per candidate, and scales
linearly. Retrieval quality measured identically at 5, 10 and 20 candidates on
this dataset, so the default was set to **10** — a 44% latency saving for no
measured quality loss. Revisit on real content, where recall may need a wider pool.

### End-to-end, as the user experiences it

| Step | Time |
|---|---:|
| Query rewrite (DeepSeek, multi-turn only) | ~600 ms |
| Retrieval (embed + search + rerank) | ~700 ms |
| DeepSeek first token | ~800 ms |
| **Perceived — first visible text** | **~2 s** |
| Full answer streamed | 3-4 s |

The typing indicator covers the first two seconds, which is why streaming matters
here beyond aesthetics: the same wait feels very different with something moving.

## End-to-end tests

`python -u scripts/smoke_test.py` — **59 passed, 0 failed**, covering:

* Streaming chat, multi-turn follow-up, out-of-scope and political refusal
* Ratings, CSAT, contact requests with reference codes and duplicate suppression
* Login, wrong-password rejection, anonymous rejection, role boundaries
* Full KB lifecycle: draft → submit → approve → publish → archive
* **Four-eyes enforcement** — author cannot approve their own entry (409)
* Review queue with transcript and retrieval diagnostics; promote-to-KB
* Analytics endpoints; audit read and hash-chain verification (12 entries valid)
* Duplicate KB content rejected with 409
* Attribution analytics: contributors, approvers, operators, activity, refusals
* Widget, demo page, console and embed script all serving

## Security tests

`python -u scripts/security_test.py` — **25 attacks blocked, 0 vulnerable**. Each
check is written as an attack and passes only when the attack fails:

* Site-key forgery; conversation hijack; cross-conversation rating
* Token forgery — garbage, tampered payload, stripped signature
* Every chat endpoint rejecting unauthenticated calls
* Scope enforcement: political, off-topic, other participants' data, prompt injection
* Queue hygiene — no contact requests without contact details
* Per-account lockout; admin surface authentication

These correspond one-to-one with the holes found in the pre-handover probe
documented in `SECURITY.md`.

## What these numbers do not tell you

* Nothing about real user questions, which will be messier than the golden set
* Nothing about answer *quality* — only whether the right entry was retrieved
* Nothing about Azerbaijani fluency; the smoke test checks characters, not grammar
* Nothing about coverage, which is the likeliest real-world failure mode

All four need real content and real traffic. See `docs/ROADMAP.md`, Phase 8.
